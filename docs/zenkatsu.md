# ゼンカツ！ 企画書

全肯定カードを使った日替わりの遊び。1日1回、お題として出されたシチュエーションに
手持ちのカード1〜3枚で答え、botたんが総評を返す。勝敗もスコアもランキングも無い。

本書は決定事項と**その理由**を残す。理由が消えると、後から「ランキングを付けよう」
「クールタイムを外そう」と戻してしまうため。

---

## 1. コンセプトと制約

### 全肯定であることが、設計の制約になる

「全肯定」をコンセプトに掲げる以上、**敗北を作れない**。これが3か所に効く。

1. **対人バトルを作れない。** ATK で殴り合えば必ず片方が否定される
2. **ランキングを作れない。** 上位を褒めることは、下位を黙って否定すること
3. **お題に不正解を作れない。** 「その編成じゃダメ」は全肯定botが言ってはいけない言葉

逆に、このプロジェクトの武器は**報酬を数値ではなく言葉で払えること**（LLM を持っている）。
数値で勝たせるのではなく「その札を選んだあなた」を毎回違う文章で肯定する。これなら
勝敗なしと再訪動機が同時に立つ。

### 帰結: スコアを表示しない

ATK/DEF/属性/種族/在庫枚数/お題との相性は、**点数化せず全部 botたん への入力にする**。
バランス調整が不要になり、出力は毎回違う文章になる。公開記録に載るのは
「出したカード」と「botたんの総評」だけ。

## 2. 命名

| 対象 | 呼称 | 備考 |
|---|---|---|
| カード体験の総称（愛称） | **ゼンカツ！** | 表記はカタカナ固定 |
| カードそのもの（説明語） | 全肯定カード | 現状維持 |
| 日替わりの一回 | 今日のゼンカツ | |
| 英語 | `Zenkatsu!` | ローマ字のまま |
| 識別子（NSID・テーブル名） | `zenkatsu` | 「！」は表示のみ |

**採用理由:**

- **動詞になる。** 〜活（就活・婚活・朝活・推し活）はそのまま「ゼンカツする」が成立する。
  「今日ゼンカツした？」が自然な一言になる。毎日戻ってくる仕掛けにとって決定的で、
  「今日の手札」「今日の三枚」等の候補にはこれが無かった
- **〜活 が「継続」を語義に内蔵している。** 一回で終わる行為を指さないので、
  「何度も遊べる」が名前を聞いた瞬間に伝わる
- `#ゼンカツ` がハッシュタグとして強い。Nagi は AT Protocol アプリで Bluesky と地続きなので、
  公開記録が外へ流れ出るときに効く
- 「全勝」「完勝」と誤読されず、勝敗の語感がゼロ

**英語を訳さない理由:** 〜活 の語感は英訳すると消えるため、訳した瞬間に名前の長所が全部死ぬ
（推し活が "oshi-katsu" で通っているのと同じ扱い）。英語圏には意味がゼロなので、
見出しに一行グロスを添える。

**注意:** 〜活 は「就活・終活」側に *やらなきゃいけない努力* の語感も持つ。
「今日もゼンカツしなきゃ」と感じさせると全肯定と逆を向く。→ 3.4 のストリーク禁止へ。

## 3. ゲームルール

### 3.1 1日の流れ

1. その日のお題（シチュエーション）が1つ提示される。全ユーザー共通
2. 手持ちから**1〜3枚**を選んで提出する
3. botたんが、お題と選んだ札を読んで総評を返す
4. 提出は**1日1回・確定**（JST 4:00 境界。`cardDrawDate()` を再利用）

### 3.2 お休み（クールタイム）

**一度出した札は、レアリティに応じた日数おやすみする。**
複数枚持っていれば在庫のぶんだけ使える（`duplicate_count` が在庫枚数になる）。

| レア | 排出率 | 期待入手 | お休み | 体感 |
|---|---|---|---|---|
| N | 68% | 1.4日に1枚 | **2日** | 主力。回転する |
| R | 22% | 4.5日に1枚 | **3日** | 準主力 |
| SR | 8% | 12.5日に1枚 | **4日** | ここぞ |
| UR | 1.8% | 55日に1枚 | **6日** | 月に数回の切り札 |
| AAR | 0.2% | 500日に1枚 | **7日** | 年に一度の大技 |

**レアリティ連動にする理由:** 排出率とお休み日数が逆相関しているので在庫が自然に釣り合う。
N は勝手に貯まるから毎日回せる、UR は持っていても週1しか出せない。
「レアを持っている人が毎日有利」という格差も生まれない。

**効果（シミュレーション実測、供給1.5枚/日・90日）:**

| | 休養なし | 休養あり |
|---|---|---|
| 最高レア札を出せる日の割合 | **100%** | **約25%** |
| 30日目の提出内訳 | N:0% R:10% SR:64% UR:23% | N:6% R:64% SR:25% UR:4% |

休養なしだと *持っている最強の3枚を永久に出し続ける* ゲームになり、卓が完全に固定化する。

**副次効果1: 被りが報われる。** `duplicate_count` は現状どこからも参照されない死に要素だった。
在庫として意味を持つことで「ガチャで被っても嬉しい」が成立する。全肯定のコンセプトとも合う。

**副次効果2: ベタ回答を封じる。** お題に対する最適な1枚があっても、昨日出していれば
おやすみ中。別の答えを探すしかない。クールタイムが大喜利の多様性装置として二役目を果たす。

**副次効果3: 公開記録が単調にならない。** クールタイムが無いと毎日同じ編成が並ぶ。

### 3.3 提出枚数は「最大3枚」の可変

**3枚固定にしない理由:** 序盤に詰む。必要在庫は `提出枚数 ×（お休み日数 + 1）` なので、
3枚固定だと常時12枚前後が必要だが、供給は1日最大2枚。最初の2週間が遊べない。

| 供給 | 1〜3日目 | 7日目 | 14日目 |
|---|---|---|---|
| 1枚/日 | 1.00枚 | 2.44枚 | 3.00枚 |
| 1.5枚/日 | 1.50枚 | 2.92枚 | 3.00枚 |
| 2枚/日 | 2.00枚 | 3.00枚 | 3.00枚 |

出せる枚数が 1→2→3 と増えていく過程が、そのまま**進行度の可視化**になる。

さらに大喜利として、**1枚で決める切れ味と3枚で物語る厚みの両方が選べる**。
「告白するときに出すカード」は1枚でビシッと決めたいし、「転校生と衝突」は3枚で描きたい。

**同じ日に同じカードは1枚まで**（3枚在庫があっても別カード3枚が必要）。種類を集める動機を残す。

### 3.4 数えないもの

**連続日数（ストリーク）は数えない。** 数えた瞬間に「途切れさせてはいけない義務」になり、
カード4番『三日坊主のリベンジャー』のテキスト *「続かなかった」ではなく「また始めた」と数える*
と正面から矛盾する。休んだ翌日に botたん が「おかえり」と言う設計にする。

## 4. お題

### 4.1 シチュエーション型にする

**行動＝シチュエーションを提示し、「そんなとき、どうする？」に札で答える。**
心情ベース（「疲れた日」）ではない。

```
パンをくわえた転校生と、曲がり角で正面衝突！　そんなとき、どうする？
```

**理由:**

1. **属性を紐づけやすい。** 具象的なぶん追い風が自然に決まる（衝突→風、朝→光、告白→火）。
   心情は抽象的すぎて属性が恣意的になる
2. **無限に書ける。** 心情は「疲れた／嬉しい／なんもない」で3ヶ月で尽きる
3. **「どんな答えでも肯定される大喜利」になる。** 大喜利は本来「面白い答えが勝つ」が、
   ここでは botたん が全部を肯定する。滑っても肯定される。そして公開記録が
   「他人の回答を読みに行く場所」に変わる（心情ベースの記録は他人のを読む動機が弱い）

**正解が1枚に見えるお題は避ける。** 「朝起きられない時」は『起床せし者』が強すぎて全員が
同じ札を出す。どの札を出しても成立する余白を持たせる。

### 4.2 追い風は「属性」を主、「種族」を副に

カード定義の分布:

| | 分布 |
|---|---|
| 属性（6種） | light 6 / earth 5 / fire 5 / dark 5 / wind 5 / water 4 — **ほぼ均等** |
| 種族（20種） | 応援族 5 が最大、**1枚しかない種族が11個** |

種族を追い風に指名すると、その1枚を持っていない人の追い風がゼロになる。
追い風＝属性、種族は「揃うと botたん が触れる」ボーナスに留める。

### 4.3 トーンに幅を持たせる

全肯定botは「しんどい日」の人も受け止める必要がある。毎日が大喜利だと、本当にしんどい日に
「パンをくわえた転校生」は白ける。**ネタ8割・素直2割**で混ぜる（日曜は素直なお題、等）。

### 4.4 LLM で生成しない

**静的 JSON の固定ローテ。** お題は全ユーザー共通で公開される上、ネタお題は品質が命なので、
量子化モデルに書かせると事故る。まず60〜100個を書き溜めてローテすれば、再登場は
「久しぶりに来た」になって許容される。カード定義と同じく、書いた資産として積み上がる。

### 4.5 例

| お題 | 追い風 | 輝く N カード |
|---|---|---|
| パンをくわえた転校生と、曲がり角で正面衝突！ | wind | スクショ職人 |
| 傘を持っていない日に限って、空が光った | wind | 傘を持ってきた予言者 |
| 深夜2時。冷蔵庫に、何もない | dark | 深夜のコンビニ探検家 |
| 推しの新グッズ。財布の中身は1,200円 | fire | 推しに供物を捧げし者 |
| 締切まであと3時間、まだ1文字も書いていない | dark | 積みゲーの番人 |
| 温泉に着いた。タオルを忘れた | water | 白湯の癒し手 |
| 目覚ましを7個かけたのに、全部止めていた | light | 起床せし者 |

## 5. 未解決の設計課題: レアリティ・インフレ

**クールタイムはレアリティ・インフレを遅らせるだけで、止めない。**

在庫は無限に増えるのにクールタイムは定数なので、どのレアリティもいずれ
「3枠を単独で埋められる」状態に達し、下位を押し出す。飽和までの日数は
`3×(お休み+1) ÷ (排出率 × 供給)`。供給1.5枚/日なら **N が9日、R が36日、SR が125日**。

実測でも N は30日で6%、**60日で0%** になり卓から消える。

構造で解こうとすると「N 専用枠」を作るしかなく、硬すぎる（R 専用枠にしても
R が12日で飽和して N は死ぬ）。

**したがってこれはお題で解く。** お題が属性を指名し、botたん が *その日のお題に噛み合った札*
に反応するなら、噛み合わない UR より噛み合う N のほうが「正しい」札になる。
スコアが存在しない設計なので、プレイヤーが良いコメントを求める限りこれは効く。

**低レアを現役に保てるかは、お題の設計と botたん の反応に懸かっている。**
リリース後に N の出現率を実測し、0% に向かうようなら追い風の効かせ方を見直すこと。

## 6. botたんの総評

報酬の本体。既存の `generateNagiCardComment.ts` を土台にする。

### 6.1 引き継ぐもの

- **Structured Outputs で ja/en を1リクエスト**（`responseSchema` に `commentJa`/`commentEn`）。
  クライアントのロケール切替が再フェッチ無しで効く既存方針に乗る
- **口調は `SYSTEM_INSTRUCTION` + `TONE_RULES_JA` を本文側にも再掲。** 独自の口調指定は書かない。
  `TONE_RULES_JA` のコメントが明言するとおり systemInstruction は入力から遠いぶん効きが弱く、
  隣に置かれた文体に負ける。**カードのフレーバーは文語調**（「〜せし者」）なので、
  まさに引きずられる条件が揃っている
- **プロンプト版数を DB に残す**（`comment_prompt_version` と同じ列）。`nagi-zenkatsu-v1` から

### 6.2 最大の罠: 肯定の対象を取り違える

既存の `NAGI_CARD_COMMENT_PROMPT_VERSION` が v2 になった理由がコード中に記録されている:

> v2:「カードに書かれた行いを、引いた人がやったことにして褒めてしまう」問題を修正。

そのため既存プロンプトは「カードに書かれている出来事を、この人が実際にしたわけではありません。
その行いを褒めてはいけません」と書いている。

**ゼンカツではこれをコピーできない。** カードは *この人が選んだ答え* だから。
しかし単純な反転も誤りで、ゼンカツには肯定対象になりうる主体が**3つ**ある。

| # | 主体 | 扱い |
|---|---|---|
| 1 | お題の出来事（転校生と衝突した） | ❌ **架空**。実際には起きていない |
| 2 | カードの行い（洗濯物を干した） | ❌ 札の説明。本人の行動ではない（v2 の教訓） |
| 3 | **その状況にその札を選んだ、という選択** | ✅ **ここだけが本人のもの** |

AGENTS.md が記録する実例（「**子供のやってる**ポケモン」→「**すいぱり**、センスが最高」の
行為者すり替え）は、まさにこの取り違え。**候補が3つに増えた状態で正しい1つを選ばせるのが、
この機能でいちばん壊れやすい部分。**

### 6.3 Gemma4-12b 向けの構造的対策

モデルは Gemma4-12b。26B より小さいぶん、6.2 の罠は**重くなる**。散文で禁止を並べるだけでは
足りないので、構造で補強する。

- **ルールは対象の隣に置く。** 主体取り違え防止は、プロンプト冒頭だけでなく
  **カードブロックの直前**にも再掲する
- **フィールド名そのものにルールを載せる。** `フレーバーテキスト:` ではなく
  `札の説明文（この人がした行動ではありません）:` にする。ラベルは値の真隣にあるので
  小さいモデルにいちばん確実に効く
- **同時に課すルールを減らす。** 禁止事項は「汎用コメント禁止」「ボケに乗る」
  「滑ったと言わない」程度に絞り、残りは出力を見てから足す

### 6.4 入力の形

```ts
export interface ZenkatsuCommentInput {
  displayName: string;
  theme: { textJa: string; textEn: string; tailwindAttribute: CardAttribute };
  /** 提出した1〜3枚。プレイヤーが置いた順は意味を持つので保つ。 */
  cards: CardDefinition[];
  /** サーバ側で決定論的に計算済みの「読み」。モデルに算術をさせないため。 */
  reading: string[];
}
```

`reading` は**文字列の箇条書きで渡す**。AGENTS.md の教訓どおり、量子化モデルに
ATK 合計を計算させてはいけない。サーバ側で判定して日本語ラベルにする:

```
- 追い風: 1枚（傘を持ってきた予言者・風属性）
- 編成の傾向: ほぼ互角（ATK合計5800 / DEF合計5600）
- 初登板: 傘を持ってきた予言者
- 何度も出している札: 深夜のコンビニ探検家（5枚目の在庫から）
- 今日いちばんの冒険: 全肯定botたん（AAR・これで7日間おやすみになる）
```

最後のラベルが効く。**「この1回のために7日間おやすみさせる」は肯定の材料として強い。**
クールタイムがここで物語として回収される。1枚だけで答えた日は `1枚で答えた` とラベルし、
それ自体を読ませる。

### 6.5 プロンプトの並び順

AGENTS.md の並び順ルール（**ユーザの入力はいちばん後ろ**）に従う。
お題と読みラベルは*指示側*、提出した札を*最後*に置く。

```
あなたのアプリ「Nagi」には「ゼンカツ！」があります。
毎日ひとつシチュエーションが出て、みんなが手持ちのカードで答えます。

# 最重要（ここを間違えないこと）
* お題は**架空のシチュエーション**です。この人に実際に起きた出来事ではありません。
  「大変だったね」と実体験のように受け取ってはいけません。
* カードのフレーバーに書かれた行いを、**この人がやったわけではありません**。
* **肯定するのは「その状況に、この札を選んだ」という選択です。**
  なぜその札なのかを自分なりに読み解いて、その読みを本人に話してください。

# ルール
* 「いい編成だね」「センスあるね」だけの汎用コメントは禁止です。
  最低1枚は名指しで、なぜそれがこの状況に効くのかを言うこと。
* ボケた答えにはボケとして乗り、真面目な答えには真面目に返してください。
  **滑っている、外している、とは絶対に言わないこと。**
* 追い風に合っていないことを欠点として指摘しないこと。
{TONE_RULES_JA}

# 今日のお題（架空のシチュエーション）
...

# この編成の読み（計算済み・そのまま使ってよい）
...

# {displayName} さんが出した札（この人の選択です）
# ※ 下の説明文は札の説明であって、この人がした行動ではありません
-----
1枚目: 傘を持ってきた予言者 / N / wind / 天候族 / ATK800・DEF1100
        札の説明文（この人がした行動ではありません）: 「...」
```

### 6.6 出力の長さは枚数に連動させる

既存はレアリティで出し分けているが（`DEEP_COMMENT_RARITIES`）、ゼンカツは**枚数**で分ける。

| 提出 | 長さ |
|---|---|
| 1枚 | 1〜2文・最大80字 — 1枚で決めた切れ味に短く返す |
| 2〜3枚 | 2〜3文・最大140字 — 札どうしの関係を読む余地がある |

答えの economy に返しの economy を合わせる。

### 6.7 ルート

`aiRoutes.ts` に `NAGI_ZENKATSU` を追加。**tier は lite-standard（FLEX にしない）。**
理由は `NAGI_CARD_COMMENT` のコメントどおりで、ユーザーが結果を見ながら待つため
待ち時間がそのまま体験の質になる。呼び出しは1人1日1回なので総量は誤差。

温度は共有既定（`ollamaDefaultTemperature()`、0.6）から始める。大喜利なので上げたくなるが、
**事実の読み取り負荷がゼロ**（ユーザーの生投稿を読まない）なぶん既定でも十分振れるはず。
上げるなら計測してから。

## 7. 画面構成

Nagi の TOP メニューに「全肯定カード」を置き、3タブで分ける。

```
全肯定カード
├ ニュース      … 今この瞬間の出来事（レアドロー・珍しいゼンカツ）
├ カードリスト  … 自分の図鑑（＝ getCards(me) の再利用。新規エンドポイント不要）
└ ゼンカツ！    … 今日のお題・プレイ・全回答の記録（日付さかのぼり）
```

```
│   ❤️3 😂5                           │
│  @someone    [白湯][スライム]        │
│   botたん「2枚で足りるって顔だね」    │
│                                   │
│              ‹ 前の日              │
└───────────────────────────────┘
```

### 7.1 公開範囲とフィード

- **グローバルのみ。** フォロワーの概念は持ち込まない
- **常時公開。** 提出前でも今日の記録は見える
- **新着順**（上が新着、下が古い）
- **日付パーマリンクでさかのぼれる。** `/zenkatsu/2026-09-18`。
  これによりお題そのものがアーカイブ資産になる

### 7.2 自由記述は入れない

**モデレーション上の大きな勝ち。** プレイヤーが打てる文字が一切ないなら、フィードに流れる
人間由来のコンテンツは「固定30枚のうちどれを選んだか」だけ。**荒らしの入力面がゼロ**になる。
審査が要るのは botたん の生成文だけで、これは既存の moderation subject に載る。

同じ理由で**非公開トグルも持たない**。露出するのは30枚のうち3枚だけで機微がほぼ無い。
「見られたくない日」への答えは、非公開で出すことではなく**出さない自由**のほう。

### 7.3 ニュースは「ハイライト」だけ

ゼンカツを全件流すと、**ニュースの約8割がゼンカツになる**（SR以上のドローが
10.0% × 1.5枚/日 = 0.15件/人日 に対し、ゼンカツは参加率50%で 0.5件/人日）。
タブを分ける意味が薄れ、本来見せたいレアドローが埋もれる。

**選別基準は 6.4 の `reading` ラベルをそのまま使う。追加のLLMコストはゼロ。**

| ニュースに載る条件 | 由来 |
|---|---|
| SR以上を引いた | ドロー時のレアリティ |
| ゼンカツに UR/AAR を出した | `今日いちばんの冒険` ラベル |
| その札の初登板 | `初登板` ラベル |
| 1枚だけで答えた | `1枚で答えた` ラベル |
| 3枚とも追い風だった | `追い風: 3枚` ラベル |
| コンボが成立した | `コンボ成立` ラベル |

#### 世界初の発見だけは、独立した項目にする

コンボの成立はハイライトだが、**そのコンボを世界で最初に成立させた回**は
`type: "comboFound"` として見出しを変える（「コンボ『××』を世界で最初に見つけた！」）。

判定の真実源は `zenkatsu_combo_discoveries` で、コンボごとに1行しか作らない
（primary key が `(combo_volume, combo_number)`）。**マイデッキの pioneer 表示と
同じテーブルを読む**ので、片方だけ「世界初」と言う状態にはならない。
専用の列もバックフィルも要らない。

**同じ提出を `zenkatsu` としては返さない。** 2項目に割ると同じ uri が一覧に2度並び、
クライアント側のリストキーが重複する。中身（お題・出した札・コンボのピル・総評）は
`zenkatsu` と同じで、変わるのは見出しだけ。

## 8. リアクション

ニュース項目とゼンカツのプレイ記録に、既存のリアクション（絵文字・Bluemoji）を付けられる。

ビューへの載せ方も既存のまま。`getZenkatsu` と `getCardNews` が `getReactionViews`
（投稿・ニュースと同じ関数）を呼び、`reactions` を項目に付ける。

**送信者は出さない。** `groupReactionViews` はリアクター一覧を subject の持ち主にだけ返すが、
その持ち主は `nagi_posts` との join で決まる。ゼンカツの提出とドローの控えは投稿テーブルに
無いので、**提出した本人が見ても匿名側に倒れる**。ニュース記事と同じ扱いで、
クライアントも `showReactors={false}` で合わせている。

`getCardNews` は未認証でも読めるが、`reactedByMe` を返すには viewer が要る。
`optionalServiceAuth` を挟み、**viewer がいるときだけ** `Cache-Control: private, no-store`
にする（未認証は `public, max-age=30` のまま）。viewer ごとに違う応答を共有キャッシュへ
載せないため。

### カード枠は開かない

`isEligibleReactionCardTrigger` の許可リストに `zenkatsu` / `cardGet` は**入れない**
（8.6 の判断）。クライアント側も同じ許可リストで報酬の請求を絞っている。
片方だけ直すと、ゼンカツにリアクションするたびサーバが 400 を返し、
報酬のエラー表示が出続ける。

### 8.1 ゼンカツの提出は PDS 権威にする（ユーザー自身の repo）

`com.suibari.nagi.reaction` の `subject` は `com.atproto.repo.strongRef` = **{uri, cid}** で、
実在する PDS レコードを指す前提。提出が AppView 権威の uuid 行だと AT-URI も CID も持たないので、
リアクションを向けるために bot 側へ別レコードを発明する必要があった。

**提出をユーザー自身の repo のレコードにすれば、この問題は丸ごと消える。**

#### なぜドローは PDS 権威にできず、提出はできるのか

`card_instances` のコメントが却下しているのは**ドロー**であって、提出ではない。両者は性質が違う。

- **ドローは乱数から価値を生む。** AppView が乱数の源でなければならず、「AAR を引いた」という
  主張には**照合先の事前状態が存在しない**。だから偽造を検出できない
- **提出は既に所持している札を参照するだけ。** 所持・お休み・1日1回のすべてを AppView が
  既に権威として持っているので、**取り込み時に照合して弾ける**

偽レコードが repo に残っても、AppView が索引しなければフィードに出ない。
これは AT Protocol の通常の動作そのもの。

#### 得られるもの

1. **リアクションが既存機構のまま動く。** `strongRef` が自然に指せる
2. **botたん repo への書き込みが約1/4に。** ゼンカツ分（0.5件/人日）が消え、
   レアドロー（0.15件/人日）だけになる
3. **Jetstream 遅延は `ensureRecord` で解決済み。** 「本人のPDSにある現在レコードを取得し、
   Nagi AppViewへ即時反映する」既存手続きがそのまま使える。
   `verifyReactionCardTrigger` が PDS を直読みしているのと同じ思想
4. **履歴がユーザーの repo に残る**（データポータビリティ）

### 8.2 レコード定義

```
com.suibari.nagi.zenkatsu    （ユーザーの repo・key: any）
  rkey:      themeDate（"2026-09-19"）
  themeDate: string
  cards:     [{ volume, number }]   1〜3枚・重複なし
  createdAt: datetime
```

**rkey を日付にする。** `at://did:plc:xxx/com.suibari.nagi.zenkatsu/2026-09-19` となり、
**repo 側でも1日1本が構造的に強制される**（同じ rkey は上書きしかできない）。
URI が人間に読めるのも利点。

botたんの総評は**ユーザーの repo に置かない**（生成物の権威は AppView 側）。
AppView の索引行に持つ。

### 8.3 取り込み時に AppView が検証すること

`validateRecord.ts` に `NAGI.zenkatsu` を足し、以下を照合する。1つでも外れたら索引しない。

- 記載の札を**その DID が所持している**か（`card_instances`）
- **お休み中でない**か（9.4 の判定）
- 1〜3枚で、**同じ札の重複が無い**か
- `themeDate` が**取り込み時点の当日**か（遡り提出の禁止）
- 同じ `(did, themeDate)` の索引が**まだ無い**か（先着のみ有効）

**新着順は record の `createdAt` ではなく AppView の `indexedAt` で並べる。**
`createdAt` はユーザーが自由に書けるので、フィード上位を取るために遡られる。
`nagiReactions` が `indexedAt` を持つのと同じ理由。

**削除の扱い:** ユーザーが `deleteRecord` したら記録からは消える（本人のレコードなので当然）。
ただし `(did, themeDate)` のロックは AppView 側に残し、**再提出はさせない**。
「1日1回・確定」はこれで保たれる。

### 8.4 ドローの控えも、ユーザーの repo に置く

ニュースに出るもう一方（カード獲得）も、ユーザー自身の repo のレコードにする。
これで**取り込み・検証・リアクション・通知が、ゼンカツとドローで完全に同じ経路**になり、
botたん の repo への書き込みはゼロになる。

#### 「ドローは PDS 権威にできない」の正確な意味

`card_instances` のコメントが却下しているのは、**ドローの結果をユーザーが決めること**であって、
ユーザーの repo に置くこと自体ではない。区別すると:

- ❌ **結果をユーザーが決める**（レコードが権威）→ 不可。照合先が無いので何でも書ける
- ✅ **結果は AppView が決め、ユーザーの repo に控えを置く** → **可能**。
  `card_draws` と `card_instances` があるので、claim が正しいか1行引けば照合できる

つまり repo にあるのは**権威ではなく控え**。ゼンカツの提出とまったく同じ防御が効く。

```
com.suibari.nagi.cardGet    （ユーザーの repo）
  rkey:      `${drawDate}-${source}`（記念日は `${drawDate}-anniv-${slot}`）
  card:      { volume, number }
  drawDate:  "2026-09-19"
  source:    "my_nagi" | "reaction" | "anniversary"
  createdAt: datetime
```

**rkey を決定論的にする。** `card_draws` の自然キー `(did, draw_date, draw_source)` に
対応させれば、再送しても上書きになるだけで重複しない。

#### 検証

- `card_draws(did, drawDate, source)` の `(card_volume, card_number)` と**一致するか**
- 記念日（`source = "anniversary"`）は `card_draws` を使わない仕様なので、
  `card_instances` の所持と `anniversaryLabel` で照合する

一致しなければ索引しない。

#### これ以降のドローだけを控える（過去は埋め戻さない）

**履歴のバックフィルはしない。** 得るものに対して手間と副作用が大きすぎる。

- ニュースは「今この瞬間の出来事」なので、何ヶ月も前のドローを控えても誰も見ない
- 所持情報は `getCards` で既に公開済みなので、ポータビリティの実利はほぼ象徴的
- 利用者が頼んでいない書き込みを、本人の repo へ何百件も撃つことになる

したがって**リリース以降に引いたぶんだけ**が控えを持ち、それ以前のコレクションは
ニュースにもリアクション対象にもならない。これは仕様として受け入れる。

ただし1点だけ拾う。ドローは AppView 側で先に確定するので、そのあとの `createRecord` が
失敗すると控えだけが欠ける（オフライン、PDS 落ち、アプリを閉じた）。**UR や AAR を引いた日に
これが起きるとニュースに出ないまま終わる**ので、`getCards` が**直近2日ぶんの取りこぼし**だけを
`unmirroredDraws` に返し、クライアントが次に開いたときに書き直す。窓をここに閉じることで、
「取りこぼしの回収」と「履歴の埋め戻し」を取り違えないようにする。

#### ニュースの並びはゼンカツと分ける

| | 日付の信頼性 | ニュースの並び |
|---|---|---|
| ゼンカツ | `themeDate` はユーザーが書く → 取り込み時に当日か検証（8.3） | **`indexedAt` 順**（遡り操作の防止） |
| ドロー | 日付は `card_draws` に AppView が持つ → 照合で確定 | **実際のドロー時刻順**でよい |

ドローの日付は検証済みなので、後から控えを書いても「3ヶ月前のURドロー」として正しい位置に
入るだけで、今日のニュースには出ない。**この違いがないと、過去ぶんの埋め戻しが
ニュースを埋め尽くす。**

### 8.5 通知

リアクションを受けたら通知に反映する。**保存側は既存のまま使えるが、生成側は2か所直す必要がある。**

`nagi.notifications` は `recipientDid` / `type` / `actorDid` / `subjectUri` / `reasonUri` の
汎用構造なので、テーブルの変更は要らない。問題は作る側。

#### 直すところ1: subject の解決が nagiPosts 限定

`applyMutation.ts` のリアクション通知は、subject を投稿テーブルにしか引きにいかない。

```ts
const subject = await tx.select().from(nagiPosts)
  .where(and(eq(nagiPosts.uri, value.subject.uri), isNull(nagiPosts.deletedAt)))
```

このままだとゼンカツへのリアクションは **subject が見つからず、黙って捨てられる**
（例外も出ないので気付きにくい）。subject の AT-URI から collection を取り出して
振り分ける形に変える。

| subject の collection | 通知の宛先 |
|---|---|
| `NAGI.post` | 投稿者（既存） |
| `NAGI.zenkatsu` | 提出者（＝レコードの持ち主） |
| `NAGI.cardGet` | 引いた本人（＝レコードの持ち主） |

#### 直すところ2: push 本文が投稿の形に固定されている

`postPushBody({ text, hasImages, hasQuote })` はテキストを持つ投稿専用。
ゼンカツはテキストを持たない（7.2 で自由記述を入れないと決めたため）ので、
種別ごとの本文生成が要る。カード名やお題を使って組み立てる。

#### botたん repo を使わないので、宛先の特殊扱いは不要

ドローの控えもユーザーの repo にあるため（8.4）、**通知の宛先は常に「レコードの持ち主」**で足りる。
bot の repo にレコードを置いていたら、素直に持ち主へ通知すると botたん に届いてしまうところだった。

#### その他

- 通知の `type` は既存の `"reaction"` を再利用する。通知一覧のクエリ（`notifications.ts`）が
  そのまま効くため。クライアントは subject の collection を見て描き分ける
- 通知一覧の hydration に、ゼンカツと cardGet の subject を足す
  （現状はリアクション行と投稿しか読んでいない）
- `deleteAccountData.ts` に、ゼンカツの提出・ドローの控え・関連通知の削除を足す

### 8.6 決めること

**`reactionCardEligibility` に `zenkatsu` / `cardGet` を加えるか。**
加えるとゼンカツにリアクションするだけで翌日のカード枠が開き、**ゲームが自分で供給を生む**。
エンゲージメントには効くが、実質の供給が 1.5→2枚/日 に寄るぶん、5 章のレアリティ・
インフレが速まる。`isEligibleReactionCardTrigger` の許可リストは意識的に編集すること。

## 9. データモデル

### 9.1 お題定義（静的 JSON）

```
packages/shared-configs/src/json/themes_v1.json   ← 真実源
packages/shared-configs/src/themes.ts             ← assertThemeDefs で起動時検証
```

`cards.ts` と同じく `id` は volume 内の連番を強制し、リリース済みの `(volume, id)` は変更禁止。

**あわせて `CARD_RACES` の定数化が必要。** 現状 `raceJa`/`raceEn` は空文字チェックだけの
自由文字列なので（`CARD_ATTRIBUTES` と違い列挙が無い）、お題が種族に触れるとタイポが静かに通る。

### 9.2 その日のお題は、テーブルに固定する

お題を「日付インデックス mod お題数」で決定論的に選ぶと、**後からお題を JSON に足した瞬間に
過去の日のお題が全部ずれる。** 日付パーマリンクでさかのぼれる設計にした以上、
これはアーカイブの破壊であり、カード番号を変更禁止にしているのと同じクラスの問題。

```ts
// nagi.zenkatsu_daily — 「この日はこのお題だった」を不変に焼き付ける
themeDate    text PK          // JST 4:00 始まり。cardDrawDate() を再利用
themeVolume  integer NOT NULL
themeNumber  integer NOT NULL
assignedAt   timestamptz
```

読み取り時に `INSERT ... ON CONFLICT DO NOTHING` で冪等に確定させれば同時アクセスでも
1つに収束する。以後 JSON をいくら増やしても過去は動かない。

### 9.3 テーブル

```ts
// nagi.zenkatsu_submissions — ユーザーの repo にある提出レコードの索引
uri                  text PK            // at://did/com.suibari.nagi.zenkatsu/2026-09-19
cid                  text NOT NULL
did                  text NOT NULL
themeDate            text NOT NULL
themeVolume          integer NOT NULL   // 提出時点のお題を焼き付ける
themeNumber          integer NOT NULL
commentJa            text               // NULL = 生成待ち（UI はコメント無しで先に表示）
commentEn            text
commentModel         text
commentPromptVersion text
reading              jsonb NOT NULL     // 6.4 の読みラベル（計算済み）
isHighlight          boolean NOT NULL   // ニュース掲載判定。reading から確定
createdAt            timestamptz        // レコードの値。表示用
indexedAt            timestamptz        // AppView が索引した時刻。**並び順はこちら**
deletedAt            timestamptz        // 論理削除。行は消さない（下記）

UNIQUE (did, theme_date)                  // 1日1回・先着のみ
INDEX (theme_date, indexed_at, uri)       // 新着順ページング
INDEX (did, indexed_at)                   // 自分の履歴
INDEX (is_highlight, indexed_at)          // ニュースタブ
```

```ts
// nagi.zenkatsu_cards — 提出した1〜3枚
submissionUri text NOT NULL
position      integer NOT NULL   // 1..3。プレイヤーが置いた順は意味を持つので保つ
cardVolume    integer NOT NULL
cardNumber    integer NOT NULL
PRIMARY KEY (submission_uri, position)
```

**削除は論理削除にする。** 本人がレコードを消したら記録からは消えるが、行は残す。
物理削除にすると **消して出し直せてしまう**（しかも zenkatsu_cards まで消えるので
出した札のおやすみもリセットされ、気に入る総評が出るまで引き直せる）。
行を残せば `(did, theme_date)` の一意索引が再提出を止め、おやすみも生き続ける。

### 9.4 クールタイム判定は1クエリで足りる

最長のお休みが7日（AAR）なので、**直近7日ぶんの提出札を取るだけ**。最大 3枚×7日＝21行。

**範囲は `theme_date` の文字列比較で取る。** 日付キーは "YYYY-MM-DD" なので辞書順＝時系列順で、
`timestamp` も `Date` も使わない。

```ts
const since = zenkatsuRestWindowStart(today);   // "2026-09-12" のような文字列
await handle.select({ ... })
  .from(nagiZenkatsuCards)
  .innerJoin(nagiZenkatsuSubmissions, eq(...))
  .where(and(
    eq(nagiZenkatsuSubmissions.did, did),
    gte(nagiZenkatsuSubmissions.themeDate, since),   // ← 文字列比較。Date が一切出てこない
  ));
```

これで **AGENTS.md が禁じている「raw sql への Date 補間」を踏む余地がそもそも無い。**
索引も `(did, theme_date)` の一意索引がそのまま効くので、追加の索引も要らない。

論理削除された提出も**数に入れる**（出した札は出したので、おやすみは続く）。

レアリティ別の判定はアプリ側で行う（21行なので自明）。実体は
`shared-configs` の `zenkatsuAvailability()` で、DB を触らない純粋関数。

### 9.5 既存スキーマは変更しない

在庫判定は `duplicate_count` を数えるだけで足りる:

```
出せる = duplicate_count > （お休み日数以内にそのカードを提出した回数）
```

個体識別は不要なので、`card_instances` の構造（`(owner, volume, number)` で1行・
`duplicate_count` が枚数）を一切変えずに済む。

```
  ドローの控え。全ドローを載せるが、ニュースに出るのは SR 以上だけ。8.4 参照
```

**提出用の procedure は作らない。** クライアントは `com.atproto.repo.createRecord` で
自分の PDS に書き、既存の `ensureRecord` で AppView に即時反映させる。
リアクションや投稿と同じ経路なので、新しい書き込み系の手続きは増えない。

`getZenkatsu` の `viewer` は、`getCards` が「自分を指定したときだけ `drawStatus` を返す」のと
同じ形。クライアントは `viewer.playable` を見て選択肢を出すが、**権威は 8.3 の取り込み時検証**。
クライアント側のチェックは UI の都合であって、防御ではない。

## 11. 実装順

```
1. [済] themes_v1.json + themes.ts + CARD_RACES 定数化
2. [済] 4テーブル（zenkatsu_daily / submissions / cards / comment_jobs）
3. [済] com.suibari.nagi.zenkatsu + validateRecord + 取り込み時検証(8.3)
        + クールタイム判定 + getZenkatsu
4. [済] 総評の生成（プロンプト + NagiZenkatsuWorker + NAGI_ZENKATSU ルート）
5. [済] cardGet（ドローの控え）+ リアクションの宛先解決 + 通知 + getCardNews
6. [済] クライアント（/cards の3タブ・ゼンカツ盤面・ロゴ）
7. [済] 記録とニュースへのリアクション（8章）+ 札のタップで拡大表示
        + コンボ世界初発見の独立項目（7.3）
```

**3 の時点でゲームとして成立するかを確かめる。** お題を見て札を出し、他人の回答が
新着順で並ぶところまでが LLM 無しで動く。ここで面白くなければ、4 に進む前にお題を見直すこと。

ワーカーは `NagiCardCommentWorker` の写しで `NagiZenkatsuWorker` を作り、
`nagi_bot_server/src/index.ts` に登録する。コメント生成ジョブの投入は、
提出レコードを索引した時点（取り込み）で行う。
