# 日記の再生成削減：実データによる先行評価

2026-10-22実施。[集計JSON](./2026-10-22-summary.json)。

## 結果と採用判断

32件の実データを各形式2回ずつ、計128リクエストで比較した。
現行の抜粋方式は64試行中26失敗（40.6%）、段落ごとの印を使う方式は64試行中0失敗だった。
**Ollamaの日記生成の既定を段落方式に変更する。** 本番反映は未実施。

| 材料 | 現行形式の初回成功 | 新形式の初回成功 |
| --- | ---: | ---: |
| Nagi・英語5件×2回 | 7/10 | 10/10 |
| Nagi・日本語の少数投稿9件×2回 | 9/18 | 18/18 |
| Nagi・日本語の複数投稿10件×2回 | 11/20 | 20/20 |
| 当日11時のBluesky利用者8人×2回 | 11/16 | 16/16 |
| 合計 | 38/64 | 64/64 |

現行形式の失敗内訳は、抜粋不一致24件、短すぎる抜粋1件、JSON途中切れ1件。
途中切れは実際に `truncated=true`、出力1024トークンで確認できた。
新形式には、抜粋不一致・全段落の印がfalse・段落構造不正・途中切れのいずれも発生しなかった。
禁止称号や不正な補助材料IDによる失敗は両形式とも0件だった。

## 比較条件

- 本番と同じOllamaのネイティブ `/api/chat` を利用。
- モデル: `hf.co/unsloth/gemma-4-12B-it-qat-GGUF:UD-Q4_K_XL`。
- モデルdigest: `596b21d708ed81243aa55b95a82dc352c2ef166dbde139f4a27949bdcc4a0494`。
- temperature=0.6、num_predict=1024、think=false。
- サーバのcontext_length=32768を確認。リクエストにnum_ctxを送っていない。
- 同時実行数1。再生成は行わず、初回の応答と検証結果を記録。
- 各case/repetitionで先に実行する形式を反転し、片側だけを常に先行させない。
- 同じ材料・演出札・モデル・予算を使用。本文の事実境界や口調の指示は共通。
- 両形式とも第1段階の修正済み、すなわちJSON全体の2100文字制限は無効。
  本比較は形式変更の効果を分離しており、旧本番の多重再試行全体を実行した結果ではない。
- 評価用の統計sinkを無効にし、本番の呼び出し統計・健康状態へ書き込んでいない。
  日記の投稿、バッジ適用、DB更新は行っていない。

## 実データの選び方と再現性

21人・32日分を使用した。

Nagiは10/15〜10/21の保存済み日記と元の削除されていない投稿から24件を選択。
同じ人だけに偏らないように人ごとの採用数を段階的に増やして選んだ。
英語の保存済み対象は5件だったため、8件へ水増ししていない。
日本語は1〜2投稿と複数投稿を含む。英語のうち3件は画像等のテキスト空欄のみで、
本番の日記生成が受け取る入力としてそのまま残した。

Blueskyは当日11時に実際に日記生成された8人の公開feedから直前24時間を再構成した。
リポストを除き、返信は含め、当日11:00より後の投稿は含めていない。
投稿数は3〜173件。現行形式の入力トークン数は8人全員で当日の本番ログと一致した。

| case | 本番ログ / 再評価の入力トークン数 |
| --- | ---: |
| 1 | 7923 / 7923 |
| 2 | 7955 / 7955 |
| 3 | 7772 / 7772 |
| 4 | 7906 / 7906 |

| 6 | 9104 / 9104 |
| 7 | 10412 / 10412 |

補助材料、呼び名、作品候補は保持されている履歴と現在の設定から一度だけ再構成し、
両形式で同じsnapshotを使った。元の送信プロンプトのbyte単位の完全再現を保証するものではない。
全caseに実際の日次補助材料があり、演出札10種類はすべて含まれる。
補助材料なし、不正なID、段落不正などは別途単体テストで確認した。

元投稿・非公開日記・生成全文は0600のローカル一時ファイルに保存し、リポジトリには含めない。
入力snapshotのSHA-256のみ集計JSONへ記録した。

## 再生成を招く理由の確認

現行方式は、同じモデルに本文とその逐語抜粋を2回書かせている。
実際に、本文にはカオス表現があるのに、抜粋の導入句だけを言い換えて失敗する例を再現した。
本文に演出がないことと、複製を間違えたことが同じ再生成へ流れていた。

最初に「段落配列＋0始まり段落番号」も予備評価した。
19応答のうち新方式10応答は構文上すべて成功したが、本文に演出があっても
別の段落番号を指す例が見つかったため打ち切った。未完了のペアは本比較に含めない。
この予備評価は上記128リクエストの集計とは別である。

採用方式は次の形。各段落を書いた直後にその段落の属性を返すため、
複製も、生成後に段落を数え直すことも必要ない。

```json
{
  "paragraphs": [
    { "text": "通常の段落本文", "containsChaos": false },
    { "text": "演出を実行した十二文字以上の段落本文", "containsChaos": true }
  ],
  "title_ja": "称号",
  "title_en": "Title",
  "usedContextId": "実在する補助材料ID"
}
```

2〜6個の非空段落、booleanの印、最低1個のtrue、印付き段落12文字以上を検証する。
本文はtextだけを空行で結び、内部用のchaosExcerptは印付き段落から機械的に取り出す。
称号・補助材料IDの検証も残す。保存形式や呼び出し元へ返すDiaryResultは変更しない。
Geminiは今回評価していないため、既定を従来の抜粋方式に維持する。

## 使用量と所要時間

| 指標（各64試行） | 現行形式 | 新形式 |
| --- | ---: | ---: |
| 入力トークン合計 | 560578 | 560156 |
| 出力トークン合計 | 30376 | 32243 |
| 平均出力トークン | 475 | 504 |
| 平均応答時間 | 8.10秒 | 8.72秒 |
| 中央値応答時間 | 8.00秒 | 8.28秒 |
| 検証失敗 | 26 | 0 |
| 正常なのにJSON全体が2100文字を超えた応答 | 6 | 11 |

新形式は1回あたりの出力が約6%増えた。1回の処理自体が速くなったという結果ではない。
再生成が必要になる失敗を取り除く点が改善であり、共有Ollamaの待ち時間を含む応答時間から
電力削減率やGPU稼働時間の削減率を断定しない。

正常な新形式の応答11件はJSON全体が2100文字を超えていた。
第1段階の文字数ガード除去も必要であり、新形式だけを入れて元のガードを残してはいけない。
今回の新形式は1024トークンで全件通ったため、日記の出力枠拡大は実施しない。

## 内容確認と限界

新形式の印付き段落64応答分を読み、演出がある段落へ印が付いていることを確認した。
Nagiの8組、Blueskyの2組は元投稿と両形式の本文を対にして確認した。
形式変更によって演出が消えた例は見つからず、既存の口調や演出札を保ったまま形式上の
再生成を減らせたため採用する。

一方、ゲーム内の行動を現実の行動に取り違える、別々の投稿の出来事を一つにつなぐ、
材料の少ない日に根拠のない活動を補う、使っていない補助材料IDを返す等の問題は両形式に残る。
印やIDが構文上正しいことは、本文内容の正確性や適切性の保証ではない。
本評価を「本文品質が改善した」「内容検証も全件合格した」という結果として扱わない。
本文品質の改善は別課題として記録し、今回の形式変更と混ぜずに評価する。

32件・各2回の観測であり、失敗率0%を将来に保証するものではない。
本番反映後は既存の新しい計測ログで、呼び出し数・理由別失敗・投稿完了・欠測を追う。
失敗上限の削減やモデル設定変更は今回行わない。

## 再実行

先に依存パッケージをbuildする。入力と生成全文はprivateな一時ディレクトリへ保存する。

```sh
node --env-file=.env scripts/exportDiaryRetryCases.mjs --since=2026-10-15 --until=2026-10-22 --out=/tmp/diary-format-eval/cases.json
AI_TEXT_PROVIDER=ollama AI_ROUTE_COMMON_USER_DIARY=ollama-chat OLLAMA_BASE_URL=http://127.0.0.1:11434/v1 pnpm exec tsx --env-file=.env scripts/evaluateDiaryRetryFormats.mts --cases=/tmp/diary-format-eval/cases.json --out=/tmp/diary-format-eval/results.json --run
node scripts/summarizeDiaryRetryFormats.mjs /tmp/diary-format-eval/results.json
```

`--run`なしなら呼び出し件数と設定だけを表示し、LLMは呼ばない。
`--count=8 --repetitions=2`で8件を各形式2回に変更できる。
exportスクリプトはNagi用。Blueskyの追加snapshotは対象8人の公開feedを別途取得したもので、
Nagi用exportを再実行するだけでは追加8件は再現されない。

両botのbuildとbot-brainの509テストが成功。ネイティブHTTP境界のmockテストで、
新形式の既定採用、Geminiの従来形式維持、本文への変換、不正な印・称号・IDの拒否、
num_ctxなし・num_predict/temperatureありを確認した。
