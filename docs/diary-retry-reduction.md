## 実装状況（2026-10-22）

第1段階を実装した。日記だけJSON全体の文字数再生成を止め、出力枠1024は維持した。
`maxTextLength: null` は共通処理で4096トークンへ連動するため、Ollamaの日記に限って
既存値を明示している。Geminiの出力枠と他機能の投稿文字数制限は変更しない。

通常ログは次のイベントを出す。本文・抜粋・称号は含めない。

| イベント | 意味 |
| --- | --- |
| `diary_ai_request` | providerへの生成呼び出し開始（通信失敗も数える） |
| `diary_ai_call` | 応答取得時の使用量・HTTP応答時間・途中切れ・出力枠・Ollama総処理時間 |
| `diary_ai operation=body` | 外側1試行の検証結果と全応答の使用量合計 |
| `diary_validation` | 抜粋の長さ、空白除去/NFCでの一致等の診断値（採否は変えない） |
| `diary_run` | 1実行の呼び出し数・応答数・外側試行数・生成完了の成否 |
| `diary_published` | 日記の投稿/保存の完了（生成完了とは別） |

生成イベントには `run_id` / `surface` / `subject` / 対象`date`を付ける。
`calls` はprovider呼び出し開始数、`responses` は応答から使用量を取得できた数。
実際にHTTPが送信される前の入力処理で例外が出た場合も開始数には入る。
応答がない呼び出しのトークン数は不明なので0相当で集計され、消費なしとは断定しない。
`diary_run completed=true` は生成成功であって投稿成功ではない。
新ログから対象日ごとの最終保存件数を調べる際は `diary_published` も確認する。

### 第1段階の観測手順

コード反映後、11時・22時を含む3日間のログを取り、旧ログの外側試行数とは別に
`diary_ai_request` の件数を実呼び出し基準値として扱う。

```sh
ssh 192.168.1.200 'journalctl -u bsky-bot -u nagi-bot --since "3 days ago" --no-pager -o short-iso --grep="diary_ai|diary_validation|diary_run|diary_published"'
```

抜粋の実態分類が必要な期間だけ、両botに次の環境変数を設定する。
期限とディレクトリは今回の収集用に決める。実装自体は収集を自動で有効化しない。

```dotenv
DIARY_DIAGNOSTICS_DIR=/var/lib/bsky-affirmative-bot/diary-diagnostics-20261022
DIARY_DIAGNOSTICS_UNTIL=2026-10-25T15:00:00Z
```

- ディレクトリと期限の両方が有効な場合だけ、検証失敗した応答を保存する。
- 最大20ファイル。排他的なファイル作成なので複数プロセス・再起動でも上限を共有する。
- 新規ディレクトリは0700、新規ファイルは0600。既存ディレクトリを指定する場合は
  運用側で0700を確認する。同じユーザーで動くbot同士は同じ保存先を利用できる。
- 保存対象はモデルの失敗応答と診断情報。元の投稿やプロンプト全体は保存しないが、
  応答自体が非公開の日記内容を含む。リポジトリには入れない。
- 期限は新規収集を止めるだけで、既存ファイルを自動削除しない。
  分類後に環境変数を外し、収集ディレクトリを削除する。
- 保存失敗は警告だけにし、日記の成否や再試行回数に影響させない。

## 再試行の構造

1. 毎時のスケジュール再走査が未完了の日記を回収する。実行中はMapで二重起動を防ぐ。
2. `generateUserDiaryResilient` が外側のラダーを実行する。
   待機基準は30秒、2分、10分、30分、60分（±20%）。期限は3時間。
3. 各外側試行で `generateUserDiaryDraft` が `generateContentWithRetry(..., 3, ...)` を呼ぶ。
   内側は `i <= retryCount` なので **初回＋再試行3回＝最大4呼び出し**。
4. JSONをパースし、段落・称号・補助材料ID・抜粋を順に検証する。
   いずれかが失敗すると、本文も称号もすべて捨てて外側から再生成する。

ラダーの設定は最大6試行だが、検証失敗は `unknown` 扱いで、共通の既定値により
実際は5試行で打ち切られる。現在のモデルでは全段が同じOllamaモデルになっている
ことをログで確認した。「モデルを上げる」というコメントどおりには動いていない。
検証失敗なら1回の起動で理論上5×4＝20呼び出しになり得る。
通信などのtransientなら外側6試行まで進み得るが、通信失敗自体は内側で再試行しない。
毎時回収は別の起動になるため、この上限は1日当たりの上限ではない。

## 原因別の評価

### A. 抜粋の失敗：最優先、ただし失敗応答の観測が必要

本文と `chaosExcerpt` を一緒に生成させ、`diary.includes(excerpt)` で照合している。
この検証が保証するのは「12文字以上の連続抜粋があること」であって、
カオス表現の質や演出札の実行そのものではない。

現在のログに失敗した本文と抜粋の組がなく、言い換え、空白・改行、句読点の違い、
本文にない抜粋などの内訳は未確定。原因を推測して正規化や曖昧一致を入れない。
任意の本文を抜粋扱いして成功させる方法も、演出の確認を形骸化するため採用しない。

評価候補は、段落配列とその段落への参照番号など、同じ文を2回生成させない形式。
既存の演出札・文体・匿名化・根拠要件を保ったまま、形式だけを変えた比較評価を行う。
抜粋だけの追加LLM修復も候補だが、必ず追加呼び出しが生じるため最初の選択肢にはしない。

### B. JSON全体の2100文字制限：確定した適用先の不整合

日記は画像（Bluesky）または日記レコード（Nagi）へ保存するが、
`maxTextLength` 未指定のため投稿用の `POST_TEXT_LIMIT=2100` が使われる。
対象は本文でなくJSON全体（称号、エスケープ、抜粋の重複を含む）。
同じ入力で最大4回生成し、最後も超過ならその応答を返している。
したがって現在の制限は厳密な公開上限でもなく、長さ以外は正常な初回応答を捨て得る。

日記に限ってJSON全体への投稿制限を外し、実際の保存・画像化・表示の制約は
本文をパースした後の仕様として確認する。共通関数の他機能の制限は維持する。
出力枠は `num_predict` を引き続き必須にし、無制限生成にはしない。

### C. JSON途中切れ：出力枠との関係が強い

5件すべてが `Unterminated string` で、直前の対応する使用量ログの出力が
1024トークン（現在の既定の `num_predict`）に達していた。
出力枠到達が疑われるが、日記ログには既存の `truncated` メタデータが出ていない。
まずそれを記録し、本文＋称号＋補助フィールドの必要量を確認する。
既定値を全機能で増やさず、必要なら日記だけの枠とプロンプト予算を一緒に調整する。

### D. 称号・段落・補助材料

段落と称号の失敗は各1件。称号の禁止語チェックは公開上の保護なので維持する。
称号だけの失敗で本文を捨てるコストはあるが、現状の頻度から後順位。
補助材料IDの失敗は今回の期間では0件。enumによる文法拘束が既にある。
検証が順番に走るため、最初の失敗より後ろの不備は現在の集計には表れない。

## 実施計画

### 1. 日記の呼び出し単位の計測と、JSON文字数再生成の除去

- 日記だけ `maxTextLength: null` とし、JSON全体の長さによる内側の再生成を止める。
- 日記の論理キー（surface・対象日・subject）、実行ID、外側試行、実呼び出し番号を関連付ける。
  `onUsage` のたびに計上し、最後の値で上書きする現状を解消する。
- 実呼び出しごとにトークン・待機を含む応答時間・Ollama生成時間・truncated・出力枠を記録する。
  応答時間にはOllamaのキュー待ちが含まれるため、GPU稼働時間とは区別する。
- 検証失敗には固定の理由コードを付ける。日記の失敗診断を他機能の自由文ログに依存させない。
- 抜粋不一致のときは本文・抜粋の長さ、空白正規化なら一致するか等を診断値として残す。
  正規化結果を採否には使わない。
- 必要な失敗応答の本文は、日記限定・件数制限・期限付きのローカル診断保存で取得する。
  常時のjournalへ利用者の投稿や非公開日記を追加しない。プロンプトdumpは入力だけなので代用不可。
- テスト: 2100文字を超える正常JSONが1呼び出しで通ること、既存の段落・称号・補助材料・
  抜粋検証が残ること、全実呼び出しの使用量が残ること、他機能の投稿制限が変わらないこと。
- この段階では再試行上限・時刻・モデル・temperatureを変えず、効果を分離して観測する。

### 2. 抜粋の形式を比較し、本文の二重生成を減らす

- 段階1の失敗サンプルを分類し、不一致の実態を確定する。
- 現行形式と「本文の段落配列＋対象段落の参照」を同一材料・同一モデルで比較する。
  日本語/英語、材料少/多、補助材料あり/なし、各演出札を含む24例を最低セットにする。
- 各条件を複数回実行し、完全一致の再現より初回成功率と分布を比較する。
  本番共有Ollamaでの評価は同時実行数1、呼び出し数を明示して実施する。
- 目視で根拠、主体・時制、演出、称号、匿名化、段落・長さを評価する。
  フィールドが正しいだけの成功を採用基準にしない。
- 形式変更により抜粋を外す場合も、演出札は残し、参照が実在することを検証する。
  内容の質が落ちた場合は採用せず、別案を検討する。

### 3. 残った失敗だけを対象に再試行を設計し直す

- 途中切れと出力枠の相関を測り、日記だけの出力枠拡大または応答形式の簡素化を比較する。
- 内容不備と通信障害を区別する。内容不備で同じ条件のまま数十分待つ効果は期待できないため、
  再試行に失敗理由を渡すか、問題フィールドだけを再生成する案を評価する。
- 称号だけの修復、毎時回収をまたぐ回数制御は、残存負荷・欠測を見て必要な場合に実施する。
- 再試行上限削減は、初回成功率を改善してから判断する。

## 検証・展開の判断基準

- 段階ごとに変更を分け、少なくとも11時・22時の両バッチを含む3日間を観測する。
- 指標: 日記1件当たりの実LLM呼び出し数/入力・出力トークン、初回検証成功率、
  理由別失敗数、完了までの時間、対象日ごとの最終欠測数。
- 目標は外側の検証失敗率を現状56.4%から10%以下へ下げること。
  日記1件当たり実呼び出し数は段階1で正確な基準値を作り、その後の削減率を測る。
  これは達成見込みを保証した数字ではなく、形式変更の評価目標。
- 初回応答の目視比較で品質を確認し、欠測・不適切な称号・根拠外の記述が増える変更は戻す。
- `num_ctx` は送らず、`num_predict` と非ゼロの既定temperatureは維持する。
- 新しい公開テキスト生成経路を作る場合は、素材に基づくURLガードも適用する。
